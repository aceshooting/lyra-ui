# Migrating from Web Awesome or Shoelace

Lyra has **no** runtime, theme, or design-token dependency on either library. It is not a fork and
carries no `wa-` / `sl-` prefix or branding. What it does do, for the components that have a
counterpart, is keep the same documented public vocabulary — attributes, slots, events, CSS parts,
CSS custom properties and methods — under the `lr-` prefix.

That makes the bulk of a migration two mechanical rewrites: the tag names, and the package import.

```
<wa-combobox value="x" multiple with-clear>  →  <lr-combobox value="x" multiple with-clear>
<wa-date-input value="2026-07-15">           →  <lr-date-input value="2026-07-15">
```

```diff
- import '@awesome.me/webawesome';
+ import '@aceshooting/lyra-ui/components/forms/combobox/combobox.js';
+ import '@aceshooting/lyra-ui/components/forms/date-picker/date-input.js';
```

A whole-package import maps to Lyra's root barrel, which registers everything and cannot be
tree-shaken. Landing on granular per-component entries instead is the one place a migration is worth
more than a rename — see [Getting started](?path=/docs/guides-getting-started--docs) for the path
shape, and the import line printed at the top of every component page here for the exact specifier.

## The rename tables

The full mapping lives in
<a href="./llms/migration.md" target="_blank" rel="noreferrer">`llms/migration.md`</a>, generated
from the mirror tables in the package README: **84** documented `wa-*` mirrors and **58** `sl-*`
ones. A tag absent from those tables has no documented counterpart — port it by hand, or check
<a href="./llms/index.md" target="_blank" rel="noreferrer">`llms/index.md`</a> for a Lyra component
that covers the same job under a different name.

Most renames are the obvious one (`wa-button` → `lr-button`). The ones that are not:

| From | To | Why |
| --- | --- | --- |
| `<wa-comparison>` / `<sl-image-comparer>` | `<lr-image-comparer>` | The two upstreams named the same component differently. |
| `<wa-data-grid>` | `<lr-table>` | Lyra's table covers the data-grid role. |
| `<wa-split-panel>` / `<sl-split-panel>` | `<lr-split>` | |
| `<sl-range>` | `<lr-slider>` | |
| `<sl-alert>` | `<lr-callout>` | |

## The codemod

The repository ships a small codemod that does the mechanical part of either migration. It is run
from a checkout of the repository — it is **not** part of the published npm package:

```bash
node packages/lyra-ui/scripts/migrate-wa.mjs --dry-run path/to/your/src   # preview only
node packages/lyra-ui/scripts/migrate-wa.mjs path/to/your/src             # apply
```

It accepts directories, files and globs, and takes `--ext=html,ts,tsx,…` to narrow the file types
(the default set covers HTML, TS/JS and their JSX variants, Vue, Svelte and Markdown/MDX;
`node_modules`, `dist`, `build` and cache directories are skipped).

**The rename table is not duplicated inside the script.** It is parsed at run time from the same
README mirror tables that `llms/migration.md` is generated from, so the codemod cannot drift out of
sync with what the library documents.

### What it rewrites

- `<wa-name` / `</wa-name` (and the `sl-` equivalents) — tag opens and closes.
- A quoted string whose **entire** content is a mapped tag name, which is the
  `customElements.get('wa-button')` / tag-name-array shape.
- The package specifiers `@shoelace-style/shoelace` and `@awesome.me/webawesome` →
  `@aceshooting/lyra-ui`, in `import`, dynamic `import()` and `require()`. That target is the root
  barrel; narrowing it to per-component entries afterwards is the follow-up described above.

### What it deliberately does not

- **Attribute names.** A rename that silently flipped an attribute's meaning would be worse than no
  rename at all, so attributes are left for you and the component's own page.
- **Deep subpath imports.** `@shoelace-style/shoelace/dist/components/button/button.js` has no safe
  mechanical target, because Lyra's layout
  (`@aceshooting/lyra-ui/components/<family>/<dir>/<file>.js`) does not mirror either upstream's.
  These are reported as warnings rather than guessed at — pick the matching entry from
  <a href="./llms/index.md" target="_blank" rel="noreferrer">`llms/index.md`</a>.
- **Components with no counterpart.** A row marked `— (extra)` in the README is never touched.
- **Text that is not a tag usage.** Prose in a comment, a longer identifier, an unrelated class
  name.

### It is best-effort, not a guaranteed 1:1 API match

Two limits are worth stating plainly.

First, the codemod is a deliberately simple, regex-based text rewriter — not an AST or HTML parser.
It anchors on the three shapes above to avoid false positives, but a quoted string that happens to
be exactly a mapped tag name while not being used as a tag would still be rewritten. **Review a
`--dry-run` before trusting it on unfamiliar code.**

Second, and more importantly: a successful rename does not prove an API match. Mirroring is a
completeness goal, not a guarantee that every attribute, default and event on every renamed tag
behaves identically. Intentional differences are always stated on the component's own page and in
its reference file — read that page for each tag you renamed, and treat the codemod's output as a
starting point you then review.

## Where the two upstreams disagree

They use different names for identical concepts. Lyra accepts **both spellings and deprecates
neither**, so whichever one you arrive with keeps working:

| Web Awesome | Shoelace | On |
| --- | --- | --- |
| `with-clear` | `clearable` | `<lr-input>`, `<lr-select>`, `<lr-combobox>` |
| `without-scroll-controls` | `no-scroll-controls` | `<lr-tab-group>` |

A deprecation warning on one of two equally valid inputs would tell half the audience their
migration was stale the day they finished it, so there isn't one.

The same principle applies to CSS parts. Where a name would otherwise have to be swapped, the
element carries **both** tokens in a space-separated `part` list (`part="label form-control-label"`
is the shape) rather than renaming — so a copied `::part()` rule keeps matching, and so does the
Lyra name. A member that quietly survives under a different name is worse than one that is missing,
because nothing about the migrated markup ever looks wrong.

## Themes and tokens

Lyra reads **only** its own `--lr-theme-*` inputs. There is no implicit compatibility layer for
another library's custom properties, and adding one would silently couple the two design systems.

For a staged migration, map your existing values onto the Lyra inputs explicitly in application CSS:

```css
:root {
  --lr-theme-color-brand-fill-loud: var(--my-existing-primary);
  --lr-theme-color-danger-fill-loud: var(--my-existing-danger);
}
```

See [Theming](?path=/docs/guides-theming--docs) for what each layer covers and how far an override
reaches.

## After the rename

1. Replace the package import and run the codemod (dry run first).
2. Open each renamed component's page here, and check the attributes, events and slots you actually
   use against its documented surface.
3. Re-check the accessibility story for anything interactive — focus order and roles are where a
   near-miss surfaces.
4. Map your theme values onto `--lr-theme-*`.
5. Register a locale if you were relying on the previous library's translations — Lyra's built-in
   strings come from its own runtime. See
   [Localization and RTL](?path=/docs/guides-localization-and-rtl--docs).

## Most of the library has nothing to migrate from

Everything marked `— (extra)` in the mirror tables has no upstream counterpart in the first place,
so there is nothing to rename: install the package and import what you need. That is the majority of
this library — every dashboard atom (stat cards, gauges, empty and skeleton states), the whole chart
family, the temporal, graph and tree components, `<lr-map>`, and the entire conversation and agent
family (chat messages, streaming states, tool-call chips and dialogs, citations, model and settings
pickers). Neither upstream ships a chat or agent UI family at all.
