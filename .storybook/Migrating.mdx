# Migrating from Web Awesome or Shoelace

Lyra is an independent implementation with no runtime, theme, token, or source dependency on
either library. Components with a documented counterpart use the corresponding public vocabulary
under the `lr-` prefix where that is safe, but a relationship is not blanket permission to rename
every use.

The checked-in migration inventory classifies all **87 Web Awesome 3.11.0** and **58 Shoelace
2.20.1** tags. Each mapping has one decision:

| Classification     | Migration behavior                                                        |
| ------------------ | ------------------------------------------------------------------------- |
| `exact`            | Prefix/package substitution is automatic.                                 |
| `rewritten`        | Automatic only with the complete declared member/default/import rewrites. |
| `warning-required` | Left unchanged with a location-aware security or behavior warning.        |
| `conceptual-only`  | A useful component relationship, never an automatic rename.               |
| `unsupported`      | No public-surface-safe automatic mapping in this release.                 |

The generated

<a href="./llms/migration.md" target="_blank" rel="noreferrer">`llms/migration.md`</a> is the authoritative per-tag list. It records the target, classification, rationale,
deterministic rewrites, and remaining public-surface differences.

## Start with the report

The package ships the version-matched `lyra-ui-migrate` CLI. Replace `<version>` with the exact
Lyra version you are migrating to:

```bash
npx --package @aceshooting/lyra-ui@<version> lyra-ui-migrate --check \
  --report=migration.json path/to/your/src
npx --package @aceshooting/lyra-ui@<version> lyra-ui-migrate path/to/your/src
```

The report is stable JSON suitable for review or CI. Each entry includes file, line, column,
origin, tag/member, action, target, and warning code. Run the `--check` pass first, resolve every
warning, apply, then run it again; the second applied pass is byte-idempotent.

The default scan covers HTML, TypeScript/JavaScript and JSX variants, Vue, Svelte, Markdown, and
MDX. Use `--ext=html,ts,tsx,…` to narrow it. Dependency/build/cache directories are skipped.

## What it can rewrite safely

For an `exact` or fully specified `rewritten` mapping, the codemod can update:

- opening/closing tags and exact tag-name string uses;
- contract-recorded attributes/properties, slots, events, CSS parts, CSS custom properties, and methods;
- explicit default-preservation attributes where the inventory declares them; and
- supported side-effect registration imports, routing them to Lyra's real
  `@aceshooting/lyra-ui/components/<family>/<dir>/<file>.js` path.

A whole-package registration import is changed only when every discovered use from that ecosystem
is automatic. That prevents a root import from being rewritten while a manual component beside it
remains under the old package.

Comments, prose, unrelated identifiers/packages, and partial strings are not treated as component
uses. Member aliases are evaluated across the whole scanned target set, so the tool cannot rewrite
a registration import while leaving a use of the old member behind in another file.

## What remains unchanged with a warning

The codemod fails closed when it cannot prove the complete transformation. Common cases are:

- `warning-required`, `conceptual-only`, `unsupported`, or unknown tags;
- imports with bindings, dynamic specifiers, and unknown deep subpaths;
- opaque framework spreads, DOM aliases, or dynamic values that hide an affected member/default;
- a polarity/security/default difference without a deterministic safe rule; and
- a conceptual target whose API still needs a manual port.

Review or expand the dynamic use, choose the exact granular target from

<a href="./llms/index.md" target="_blank" rel="noreferrer">`llms/index.md`</a>
, and rerun. A warning is intentionally not converted into markup that parses
cleanly but has inert members.

## Upstream mappings to review

Most compatible relationships keep the suffix (`wa-button` → `lr-button`). These upstream mappings
deserve an explicit check:

| Source | Target | Note |
| --- | --- | --- |
| `<wa-comparison>` / `<sl-image-comparer>` | `<lr-image-comparer>` | Different upstream names for the same before/after role; follow the generated classification before renaming. |
| `<sl-range>` | `<lr-slider>` | Different tag name; review the value/event detail contract. |
| `<wa-split-panel>` / `<sl-split-panel>` | `<lr-split-panel>` | Exact two-pane separator; the richer multi-pane `<lr-multi-split>` is a separate Lyra component. |
| `<sl-alert>` | `<lr-alert>` | Closed by default, with alert lifecycle/countdown and identity-preserving `toast()`. `<lr-callout>` remains the Web Awesome callout relationship. |

The corresponding granular registrations are:

```js
import "@aceshooting/lyra-ui/components/lr-split-panel.js";
import "@aceshooting/lyra-ui/components/lr-alert.js";
import "@aceshooting/lyra-ui/components/lr-image-comparer.js";
```

Page and media mappings use the same stable tag-shaped registrations:

```js
import "@aceshooting/lyra-ui/components/lr-page.js";
import "@aceshooting/lyra-ui/components/lr-video.js";
import "@aceshooting/lyra-ui/components/lr-video-playlist.js";
```

For the separately supported legacy Lyra profile, see the generated CLI/API reference in
[`llms/migration.md`](./llms/migration.md). This guide focuses on migrations from Web Awesome and
Shoelace.

## Security-preserving differences

Some incompatibilities are deliberate and remain manual:

- `<lr-include>` sanitizes every fragment, has no script-executing mode, and defaults to
  `mode="same-origin"` rather than `cors`. Cross-origin or script-dependent uses get a warning.
- Link-like Lyra controls always add `noopener noreferrer` when `target` is set and always strip
  `opener`. `<lr-button>` and `<lr-breadcrumb-item>` also preserve independently set author tokens
  such as `nofollow`, `me`, and `license`; those tokens cannot remove the security floor.
- `<lr-zoomable-frame>` rejects active/non-embeddable schemes, always carries a sandbox, and never
  combines `allow-scripts` with `allow-same-origin`.
- Remote media/viewer inputs retain Lyra's URL validation, byte/entry/row caps, sanitization, and
  stale-request guards.

These differences are part of the target contract, not omissions the migration should hide.

## Where the two upstreams disagree

Lyra accepts both spellings for equivalent public concepts and deprecates neither:

| Web Awesome               | Shoelace             | On                                           |
| ------------------------- | -------------------- | -------------------------------------------- |
| `with-clear`              | `clearable`          | `<lr-input>`, `<lr-select>`, `<lr-combobox>` |
| `without-scroll-controls` | `no-scroll-controls` | `<lr-tab-group>`                             |

Where a CSS part needs two public names, Lyra puts both tokens on the same rendered node rather than
swapping one for the other. A copied `::part()` selector therefore keeps matching whichever
upstream vocabulary it used.

## Themes and tokens

Lyra reads only its own `--lr-theme-*` inputs. Map existing values explicitly in application CSS;
there is no implicit competitor-token compatibility layer:

```css
:root {
  --lr-theme-color-brand-fill-loud: var(--my-existing-primary);
  --lr-theme-color-danger-fill-loud: var(--my-existing-danger);
}
```

See [Theming](?path=/docs/guides-theming--docs) for the token layers and override reach.

## After the migration

1. Resolve every report warning; do not treat a changed prefix as proof of API compatibility.
2. Replace broad imports with the exact granular modules shown on each component page.
3. Check the documented attributes, defaults, slots, events, parts, and methods you actually use.
4. Exercise keyboard/focus behavior and the populated accessibility story for interactive surfaces.
5. Map theme inputs and register/select the locales the application offers. Set `dir="rtl"`
   explicitly for RTL layouts; locale selection alone does not change direction.
6. Run the codemod again and keep the no-change report as migration evidence.
