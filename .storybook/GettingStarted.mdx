# Getting started

Lyra UI is a library of plain custom elements. There is no wrapper, no provider, no build plugin
and no framework binding to set up — you install the package, import the elements you want, and
write HTML.

## Install

```bash
npm install @aceshooting/lyra-ui
```

`lit`, `@floating-ui/dom` and `@types/geojson` come along as ordinary dependencies, so nothing else
is required to render a button, a form, a table or a dialog.

Everything heavier than that is an **optional peer dependency** — Chart.js for `<lr-chart>`,
MapLibre for `<lr-map>`, PDF.js for `<lr-pdf-viewer>`, and so on. Component-facing peers are normally
loaded on demand and fail closed with a localized error if unavailable; `<lr-phone-input>` instead
accepts a consumer-built phone-number adapter, while the React/Vue/Svelte peers are types-only. You
only install the peers for surfaces you actually use. See the
[Optional peers](?path=/docs/guides-getting-started--docs#optional-peers) note below.

## Registering an element

Every component is its own side-effect entry point that registers its own tag:

```js
import '@aceshooting/lyra-ui/components/lr-button.js';
```

```html
<lr-button variant="brand">Save changes</lr-button>
```

That's the whole setup. The import registers `<lr-button>` with `customElements`, and any
`<lr-button>` in the document — including ones added later — upgrades itself.

**The stable registration path is derived from the tag**:
`@aceshooting/lyra-ui/components/<lr-tag>.js`. It stays valid if the component's internal family
folder moves. Family-shaped registration paths remain compatible, and `.class.js` imports still
use the owning family path when you need the class without defining its tag.

You never have to work the path out by hand: **every component page in this site prints its own
import line directly under the title**, and the same line appears in that component's reference file
under <a href="./llms/index.md" target="_blank" rel="noreferrer">`llms/index.md`</a>.

Some directories hold more than one tag, and each tag is registered by its own entry point. Tabs are
the common example:

```js
import '@aceshooting/lyra-ui/components/lr-tab-group.js';
import '@aceshooting/lyra-ui/components/lr-tab.js';
import '@aceshooting/lyra-ui/components/lr-tab-panel.js';
```

```html
<lr-tab-group>
  <lr-tab panel="general">General</lr-tab>
  <lr-tab panel="advanced">Advanced</lr-tab>
  <lr-tab-panel name="general">General settings</lr-tab-panel>
  <lr-tab-panel name="advanced">Advanced settings</lr-tab-panel>
</lr-tab-group>
```

The v8 Page and media surfaces use the same granular convention, as do the compatibility tags that
preserve displaced Lyra behavior:

```js
import '@aceshooting/lyra-ui/components/lr-page.js';
import '@aceshooting/lyra-ui/components/lr-video.js';
import '@aceshooting/lyra-ui/components/lr-video-playlist.js';

import '@aceshooting/lyra-ui/components/lr-native-time-input.js';
import '@aceshooting/lyra-ui/components/lr-pan-zoom.js';
import '@aceshooting/lyra-ui/components/lr-split-panel.js';
import '@aceshooting/lyra-ui/components/lr-alert.js';
```

## The two import styles

### Granular subpaths — the default

```js
import '@aceshooting/lyra-ui/components/lr-input.js';
import '@aceshooting/lyra-ui/components/lr-select.js';
import '@aceshooting/lyra-ui/components/lr-option.js';
```

One import per tag you use. Your bundler sees exactly those modules and their shared internals, and
nothing else. This is what you want in application code, and it is what every example in these
guides and in the component reference uses.

### The explicit all-components entry — for exploring

```js
import '@aceshooting/lyra-ui/all.js'; // registers every root-included component
```

Convenient in a scratch file, a REPL, or while you are still deciding which components you need.
The package root itself is a pure named-export surface in v8 and registers no tags.

Two things to know before you ship it:

- **It defeats tree-shaking.** The barrel's entire purpose is the side effect of registering every
  tag, so a bundler cannot drop any of it. Importing the barrel to use three components pulls in all
  of them.
- **It is not actually complete.** `all.js` deliberately skips 15 inventory-designated
  optional-peer-family tags — the whole chart family (`<lr-chart>` and its typed subclasses, `<lr-box-plot>`,
  `<lr-histogram>`), plus `<lr-map>`, `<lr-graph>`, `<lr-knowledge-graph-explorer>` and
  `<lr-geojson-view>`. Their peers still load lazily, but those tags are intentionally outside the
  broad root registration surface and always need their own subpath import.

The package root re-exports a broad compatibility surface of commonly used classes, helpers and
types without registering components. A component's own entry point remains its complete contract.

### Family entry points

Every one of the eleven families ships an "everything in this family" entry —
`@aceshooting/lyra-ui/components/<family>`, with no trailing path:

```js
import '@aceshooting/lyra-ui/components/conversation'; // every conversation element
import '@aceshooting/lyra-ui/components/forms';        // every form control
```

The eleven keys are `agent-tools`, `charts`, `conversation`, `data`, `forms`, `layout`, `media`,
`overlays`, `retrieval`, `utility` and `viewers` — the same segments the granular paths use. Each
entry registers *and* re-exports the complete family. (Only three of these were documented before
8.0.0, which made the other eight effectively unreachable even though they were in the `exports`
map.)

A family barrel is **side-effectful by design**: importing it registers every tag in that family,
just as `all.js` registers its root-included set. Reach for one when you genuinely use most of a
family and want a single import; reach for the granular
`@aceshooting/lyra-ui/components/<lr-tag>.js` path — which is what every example in
these guides uses — when you do not, **because a barrel cannot be tree-shaken down to the two
elements you actually render**. Granular entries remain the recommendation for production.

One difference from the root barrel: a family entry **does** register the peer-gated tags its family
owns — the whole chart family under `charts`, `<lr-map>` under `media`, `<lr-graph>` and
`<lr-knowledge-graph-explorer>` under `retrieval`, `<lr-geojson-view>` under `viewers`. That still
costs nothing up front, because every peer is loaded by a dynamic import at render time; registering
a tag never pulls Chart.js, MapLibre or d3 into your first-paint bundle. It does mean the tag exists
and will fail closed with a localized error if you render it without installing its peer.

## Loading arbitrary Lyra markup on demand

The optional manual autoloader is side-effect-free: it imports only inventory-known tags that are
actually rendered, without pulling the root barrel into the application entry chunk.

```ts
import { discover, start, stop } from '@aceshooting/lyra-ui/autoloader.js';
import { allDefined } from '@aceshooting/lyra-ui/utilities/defined.js';

await discover(document); // scan once
await start(document);    // scan, then observe dynamic/Turbo-style replacements
await allDefined(document);
stop();
```

Both scans include caller-owned open shadow roots and scoped custom-element registries. A loader-owned
`data-lr-autoload-pending` marker remains through the component's first update, so application CSS
can avoid a flash of undefined content. `{ events: true }` enables bubbling/composed
`lr-autoload-preload`, `lr-autoload-loaded`, and `lr-autoload-error` events. Failed imports clear
their marker and can be retried by a later scan.

Optional-peer tags are excluded unless every required package is explicitly allowed:

```ts
await start(document, {
  optionalPeers: ['dompurify', 'postal-mime'],
  events: true,
});
```

The side-effectful `@aceshooting/lyra-ui/autoloader-cdn.js` entry auto-starts for an ESM CDN. Put
`data-lyra-autoloader` on its script when the CDN wraps module URLs; script-local
`data-lyra-optional-peers="dompurify,postal-mime"` and `data-lyra-autoload-events` configure the
same policy. Both autoloader entries are Node-safe no-ops without a document. `allDefined()` loads
nothing itself: call it after explicit registrations or the autoloader when a test/bootstrap path
needs every currently rendered known tag and its first update to be ready.

## Importing a class without registering a tag

Every registration entry has a `.class.js` sibling that exports the class — and its
`HTMLElementTagNameMap` augmentation — without touching `customElements`:

```ts
import { LyraTable } from '@aceshooting/lyra-ui/components/data/table/table.class.js';

const table = document.querySelector('lr-table') as LyraTable<Invoice>;
```

Use it for subclassing, `instanceof` checks, and type-only imports. Note that
`document.querySelector('lr-table')` is only *typed* as `LyraTable` when that class module is in
your type graph — importing the registration entry (`table.js`) is enough, since it re-exports the
class module.

`theme.js`, `localization.js` and `events` are deliberately free of component imports, so an
application can set up theming, locales and event typing without pulling the component graph into
its first-paint bundle.

### Installing the theme

`theme.css` is optional — every component renders correctly with no theme configured, because each
internal token falls back to a built-in value. Import it once at the application root when you want
the ready-made light and dark palettes:

```css
@import '@aceshooting/lyra-ui/theme.css';
:root { --lr-theme-color-brand-fill-loud: #7c3aed; }
```

**The order you load it in does not matter.** `theme.css` declares its own cascade layers up front
(`@layer lr-base, lr-theme, lr-utilities, lr-overrides;`) and puts its tokens in `lr-theme`. Any
declaration you write *outside* a layer beats every layered one, whatever its specificity and
whatever the source order — so the `:root` override above wins even if your stylesheet is bundled
before `theme.css`, and it needs no `!important`. `lr-utilities` and `lr-overrides` are named so you
can opt your own layers into a defined position relative to Lyra's rather than inventing one.

Switch modes with `class="lr-light"` / `class="lr-dark"` (or `data-lr-theme="light"` / `"dark"`) on
any ancestor. [Theming](?path=/docs/guides-theming--docs) covers the token layers, how far an
override reaches, and the `theme.js` runtime for persisting the choice.

## Optional native styles and utilities

The light-DOM styles are separate from every component entry and from `theme.css`. Import either
one independently; importing neither preserves the browser and application styles you already have.

```css
@import '@aceshooting/lyra-ui/native.css';
@import '@aceshooting/lyra-ui/utilities.css';
```

`native.css` never installs a page-wide reset. It styles native elements only when they are
**descendants** of `.lr-native`; the element carrying the marker is not reset itself. This makes an
existing region an explicit boundary:

```html
<section class="lr-native lr-stack">
  <h2>Profile</h2>
  <label for="display-name">Display name</label>
  <input id="display-name" />
</section>
```

`utilities.css` uses exact class selectors wrapped in `:where()`. Its main groups are display and
composition (`lr-flex`, `lr-grid`, `lr-stack`, `lr-cluster`, `lr-grid-auto`), wrap/alignment/gap,
logical sizing and overflow, text/prose, `lr-visually-hidden` / `lr-visually-hidden-focusable`,
`lr-fouce-hidden`, and the `lr-page-mobile-only` / `lr-page-desktop-only` helpers. The Page helpers
follow `<lr-page view="mobile|desktop">`, which is derived from that Page's allocated inline size;
they do not consult the viewport.

Both files declare the same order as `theme.css`: `lr-base`, `lr-theme`, `lr-utilities`, then
`lr-overrides`. Native styles live in `lr-base` and utility classes in `lr-utilities`, so ordinary
unlayered application CSS remains authoritative regardless of import order. All design values come
from Lyra tokens; the complete class inventory and bundle-specific override hooks are in
<a href="./llms/shared.md#optional-native-styles-and-css-utilities" target="_blank" rel="noreferrer">llms/shared.md</a>.

### External modal interop

If a third-party modal opens above a Lyra modal, yield Lyra's document-level Escape, Tab, and inert
ownership for the connected external root:

```ts
import { suspendLyraModalsFor } from '@aceshooting/lyra-ui/utilities/overlay-manager.js';

const externalModal = document.querySelector<HTMLElement>('#vendor-modal')!;
const release = suspendLyraModalsFor(externalModal);
// When the external modal closes:
release();
```

The release function is idempotent, document-scoped, and nestable. Lyra preserves its own stack and
focus-return targets while suspended; disconnecting or adopting the external root releases it
automatically.

## Optional peers

Most component-facing peers are imported dynamically the first time a component renders something
that requires them. If one is not installed, the component fails closed and renders a localized
error in a live region rather than throwing. Empty-but-valid results get their own state and never
take the error path. `<lr-phone-input>` is the exception: it accepts a consumer-created adapter and
never imports `libphonenumber-js` itself. React, Vue, and Svelte are compile-time declaration peers,
not component runtimes.

Install only what you use:

```bash
npm install chart.js          # <lr-chart> and its typed subclasses
npm install maplibre-gl       # <lr-map>
npm install dompurify         # <lr-include>, and the viewers that render remote HTML
```

The full component-to-peer table is in
<a href="./llms/peers.md" target="_blank" rel="noreferrer">`llms/peers.md`</a>.

## Using them from a framework

They are custom elements, so they work anywhere. React/JSX, Vue, and Svelte projects can opt into
generated declarations once in their type graph; these entries emit empty JavaScript, add no
wrapper dependency, and do not register tags:

```ts
import type {} from '@aceshooting/lyra-ui/custom-elements-jsx';
import type {} from '@aceshooting/lyra-ui/vue';
import type {} from '@aceshooting/lyra-ui/svelte';
```

Continue importing the granular registration modules for the elements the application renders.
Two runtime caveats apply to custom elements in general, not to this library specifically.

**Complex values must be property-bound, not attribute-bound.** An attribute stringifies, so
`rows="[object Object]"` is what an array binding gets you. Use your framework's property syntax:

```jsx
// Lit
html`<lr-table .rows=${rows} .columns=${columns}></lr-table>`
// Vue
<lr-table :rows.prop="rows" :columns.prop="columns" />
// Angular
<lr-table [rows]="rows" [columns]="columns"></lr-table>
// React 19+ passes objects to custom-element properties natively
<lr-table rows={rows} columns={columns} />
```

**Events are dashed custom events**, not React-style `onSomething` props:

```jsx
html`<lr-table @lr-sort=${onSort}></lr-table>`   // Lit
<lr-table @lr-sort="onSort" />                    // Vue
<lr-table (lr-sort)="onSort($event)"></lr-table>  // Angular
tableRef.current.addEventListener('lr-sort', onSort); // React
```

Angular additionally needs `CUSTOM_ELEMENTS_SCHEMA` in the module or component that uses the tags.
And remember that in-DOM HTML lower-cases attribute names — a camelCase *property* name only
survives in framework templates and in JavaScript, never in hand-written HTML.

## SSR and declarative shadow DOM

Root and granular component imports are server-safe under Node 20+. Import the public loader before
any other module that can import Lit. Its machine-readable matrix classifies every tag into one of
two initial-render tiers:

- `render-and-hydrate` emits Declarative Shadow DOM and reuses the server nodes in the browser.
- `client-render` preserves the host, serializable attributes, and light DOM on the server, then
  creates shadow DOM on upgrade for components that need layout, canvas, observers, media, or other
  browser APIs during their first render.

```ts
import {
  lyraSsrElementRenderers,
  LYRA_SSR_SUPPORT_MATRIX,
} from '@aceshooting/lyra-ui/ssr-loader.js';
import { render, LitElementRenderer } from '@lit-labs/ssr';
import { html } from 'lit';

const result = render(html`<lr-page><main>Dashboard</main></lr-page>`, {
  elementRenderers: lyraSsrElementRenderers(LitElementRenderer),
});
```

The fallback renderer must precede `LitElementRenderer`. Property bindings cannot be serialized in
the fallback tier, remote content remains client-only, and layout/observer/canvas/media work begins
after hydration. `getLyraSsrMode()` and `diagnoseLyraHydration()` expose the declared tier and live
readiness diagnostics; optional-peer components still need their granular registration import.

## Component status and deprecation

Every component page carries a `stable` or `experimental` status and the first published `since`
version. Stable means production-ready. Experimental means the design is still under review, but a
published experimental API receives the same semver protection as a stable one.

A deprecation is separate, explicit metadata: it names the replacement, rationale, deprecation
version, and earliest removal version. An API deprecated in major M remains through the complete
M+1 release line and cannot be removed before M+2. The machine-readable metadata powers the same
badges and notices in Storybook, the Custom Elements Manifest, editor data, and the LLM reference.
